MedicalCohortDemo

Microsoft Fabric brings data from every source into OneLake,
and every workload reads that one copy.

Microsoft Fabric is a software‑as‑a‑service data platform. Its workloads run on shared compute capacity and keep their data in OneLake, the organization’s data lake, which is built on Azure Data Lake Storage. Data in other clouds and systems can be added to OneLake with a shortcut, which reads it from the source, or with mirroring, which keeps a replica up to date. About this demo

The question the demo answers, and the data it uses.

A research team wants patients for a study, for example former smokers aged 50 or over with a lung nodule of at least 6 mm on CT. Once the patients are found, the team needs their records, images and reports. That information is split between the EHR, the PACS and the clinical documents, which are separate systems with their own identifiers.

The demo builds a research data platform for this in one Fabric workspace, with 3,539 synthetic patients. The study question above finds 358 of them. The sections below follow the data from the source systems to the research team.

The demo

    The data starts in four places. The Epic Clarity and Caboodle tables can be in SQL Server on premises, Snowflake, Azure Databricks or another Fabric workspace (this demo writes them straight into OneLake), the PACS index is in the imaging vendor’s cloud, and 262,171 DICOM images and 17,910 clinical documents are in Azure Data Lake Storage. Fig 1 shows how each one is connected to OneLake.

    • Data already stored as open files, such as Iceberg or Delta tables and DICOM folders, is connected with a shortcut. Fabric reads the files from the source.
    • Databases in use, such as the PACS index or SQL Server, are mirrored. Fabric keeps a Delta replica of each one up to date.

    Afterwards the workspace holds 62 tables and about 280,000 files, linked by MRN and accession number.     Legacy and vendor formats

    Some systems have no open export format. Data Factory copies their data into OneLake as raw files, and a Spark notebook converts the files to Delta tables.

    Data Factory’s IBM Db2 connector reads Db2 on an AS/400 through the on‑premises data gateway, and pipelines copy mainframe and vendor files byte for byte. A Spark notebook then decodes the EBCDIC records with their COBOL copybook, for example with the open‑source Cobrix library, and writes Delta tables.

    A medallion architecture keeps data in layers. Bronze holds the data as each source delivered it, Silver holds it cleaned and in a standard model, and Gold holds it shaped for a particular use. In this demo Silver is the OMOP Common Data Model and Gold is an i2b2 star schema for cohort queries.

    • In Bronze, the DICOM headers were given the Epic patient identifiers, and the PACS gained 2,651 nodule findings from the radiologists’ annotations.
    • Two Fabric notebooks build the other layers, Silver_OMOP_Build from Bronze and Gold_i2b2_Build from Silver, so both can be rebuilt after a source changes.

    Why the demo uses OMOP and i2b2

    Both are open data models that research hospitals already run. Building both lets the same study question be checked in each.

    OMOP CDM v5.4Silver

    Maintained by
    OHDSI, an open science community
    Used by
    ATLAS and the HADES R packages for observational research, and healthcare data solutions in Microsoft Fabric
    Strength
    Standard vocabularies. A concept such as “Nodule of lung” finds every code below it, whichever system the code came from

    i2b2Gold

    Maintained by
    The i2b2 tranSMART Foundation. i2b2 is open source and was first built at Harvard and Mass General Brigham
    Used by
    The i2b2 query tool, and SHRINE, which connects the academic medical centers of the ACT network
    Strength
    An ontology tree with a patient count on every folder, for checking how many patients a study could recruit

    i2b2 can also run directly on an OMOP database. In this demo Gold is a separate copy that carries no source identifiers; the mapping to the Epic IDs stays in Silver.

    A semantic model sits between the tables and the people who ask questions. It names the tables, relates them and holds shared measures, such as an obfuscated patient count. Every report and agent that uses the model counts the same way.

    • Researchers use Cohort Discovery (i2b2) for patient counts.
    • Reviewers use Cohort Requests to approve or reject data requests.
    • The honest broker uses Research Data (OMOP) for the patient-level records of approved requests.

    All three models are in Fabric IQ, the Fabric workload for semantic models and ontologies. Its MCP server is how GitHub Copilot asks the Cohort Discovery model questions in plain language, as the Cohort Discovery step of Fig 4 shows.

    Before any patient data is released, a research team checks how many patients match its study’s criteria. In this demo the researcher asks in plain language in the Cohort Discovery app. GitHub Copilot turns the question into an i2b2 query and runs it on the Cohort Discovery semantic model, and the run is stored in i2b2’s query tables.

    • Counts are obfuscated the way i2b2 does it. Random noise is added, and a count of 3 or fewer is shown as “Fewer than 4”.
    • Every run gets a QUERY_MASTER_ID. When the researcher is happy with a run, they submit it as a data request, and a reviewer approves or rejects it in the approval app.

      Patient 360 is a Fabric App (Rayfin) that puts one patient’s whole record on one page: the Epic visits, problems, orders and results, the studies in the PACS, the DICOM images in the archive, and the typed and scanned reports. It reads each source where it is, through the SQL analytics endpoint of its Patient360 lakehouse, which holds only a patient index and the viewer files made from the DICOM.

      • 3,539 hospital patients, all synthetic, and 15 research patients from TCGA with their tumour genomes and AI lymphocyte maps. 27 of them are demo patients, picked to show every kind of image.
      • Images open in the record’s own viewers: CT and MRI with the radiologists’ nodule outlines, X-rays, and whole-slide images at up to 40×.

      Ask is a conversation with GitHub Copilot inside Patient 360, about one patient, several or all of them. Copilot answers with the record’s own viewers drawn in the answer, and the answer lists each step Copilot took, with its time.

      • Every tool runs in the page, through the same functions and signed links as the record. The chat relay, a Container App running the Copilot SDK, carries the question, the tool calls and their results between the page and Copilot.
      • Each reader signs in with GitHub, so the questions run on their own Copilot plan. The answers are for education and research and leave clinical decisions to the treating team.

      Summary

      The path the demo followed, from the source systems to the research team.

      The EHR tables, the PACS database and the images and documents reached OneLake as Bronze lakehouses and a SQL database. Notebooks built OMOP in Silver_OMOP and i2b2 in Gold_i2b2 from them, and three semantic models in Fabric IQ serve the honest broker, the researchers and the reviewers. GitHub Copilot asked the Cohort Discovery model the study question in plain language and found 358 patients, shown as 356 ±3.

      The request was approved in a Rayfin app on Fabric. A Data Factory pipeline delivered 25 of the patients in demo mode to a lakehouse of their own in about two minutes, with their imaging studies linked by shortcut, and the research team explored them in a notebook that runs in about a minute. All of it ran in the workspace MedicalCohortDemo, on one F8 capacity.

      Patient 360, a second Rayfin app in the same workspace, puts one patient’s whole record on one page and reads each source where it is, with the CT, the slides and the tumour genome in their own viewers. On its Ask page GitHub Copilot answers questions about one patient or several with those viewers and lists each step it took.
